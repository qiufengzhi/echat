# 下行弱网拥塞控制

> 把 SFU 下行从「固定 20ms 节拍 + 队列满了丢最老」改成「按估计带宽平滑发送」
>
> 实测数据见 `test-results.md`

## 一、结论

**改了什么**：补上出向 transport-wide 序号（原来反馈链是断的）、接入发送侧带宽估计、用有界令牌桶替换无界漏桶、加订阅者健康状态机与房间级码率降档。

**实测收益**（30kbps 链路、52kbps 需求，3 轮 × 30s，同镜像切开关做 A/B）：

| 指标 | 关闭控制 | 开启控制 | 变化 | 显著性 |
|---|---|---|---|---|
| 连续丢 ≥3 帧占比 | 16.96%（322/1899） | 14.00%（282/2014） | **-17.4%**（95% CI −4.1%~−30.8%） | z=−2.56，**p=0.011** |
| RTCP 丢包 p99 | 89.6% | 74.5% | -15.1pp | — |
| 平滑发送排队延迟 p99 | 不适用 | 49.6ms | — | — |
| 目标码率 | 不适用 | 23.4kbps | — | — |
| 会话成功率 | 100% | 100% | 持平 | — |

**已知边界**：

1. **只对拥塞丢包有效**。随机丢包（`netem loss`）下三档差异均不显著（p=0.23~0.43），因为少发不会减少误码。这是原理边界，不是实现缺陷
2. **幅度未达设计目标**。设计写的是 −30%，实测 −17.4%；链路 30kbps 换算成 RTP 层只有 21.2kbps，而 Opus 最低档 16kbps 加上头约 21kbps，几乎没有余量
3. **置信区间宽**。只能证明「有改善」，不能把 17.4% 当作精确值

## 二、为什么要改

改造前的发送路径是这样：

```
应用按 20ms 节拍写包 → 中继队列（无界 list）→ 立刻写 socket
```

六个断点：

| # | 断点 | 后果 |
|---|---|---|
| 1 | 出向包没打 transport-wide 序号 | 浏览器无从建索引，TWCC 反馈为空；`ConfigureTWCCSender` 只注册了「用收到的包生成报告」，缺的是「给出向包打序号」 |
| 2 | 中继队列无界 | 慢订阅者让队列单调增长，延迟无上界 |
| 3 | 队列满时丢弃最老 | 语义正确但没有速率概念，突发全靠缓冲吸收 |
| 4 | 发送速率与链路容量无关 | 链路 40kbps 也照发 52kbps，多出的部分变成丢包 |
| 5 | 晚加入者的中继轨没接 RTCP | 该出流的抖动/丢包/RTT 永久缺失 |
| 6 | 编码码率固定 32kbps | 拥塞时没有任何降档手段 |

## 三、方案

四个部件，各自解决一层：

| 部件 | 作用 | 关键点 |
|---|---|---|
| **带宽估计** | 根据 TWCC 反馈估算链路能承载多少 | 复用 pion 自带的 GCC；它不实现拦截器接口，需自写适配层 |
| **有界平滑发送器** | 按估计值匀速发送 | 自研令牌桶，队列双上限，溢出丢队首 |
| **健康状态机** | 判断这个订阅者还能不能用 | 双阈值滞回 + 停留时间 + 断连确认 |
| **房间码率策略** | 拥塞时降编码码率 | 编码器房间共享，所以降档只能按房间做 |

**装配顺序**（顺序错了估计器会静默失效）：

```
Nack → SR 时钟 → RTCP 报告 → TWCC 发送器 → 带宽估计 → transport-wide 序号
                                                    ↑            ↑
                                              必须在序号之前   必须在最外层
```

推导依据：`Chain.BindLocalStream` 后注册的在外层。序号要在包进入发送队列**之前**写好，估计器的发送时刻记录才有效。

### 3.1 平滑发送参数

| 参数 | 取值 | 依据 |
|---|---|---|
| 队列包数上限 | 2 包 | 2 × 25ms = 50ms 排队上限，与「p99 ≤ 60ms」自洽；3 包时实测 73.5ms 超标 |
| 队列字节上限 | 700B | 防止小包场景绕过包数限制 |
| 出队节拍 | 5ms | 20ms 帧长的四分之一 |
| 令牌桶容量 | 1.5 × 单帧字节 | 允许一次小突发，又不至于撞进路由器浅队列 |
| 开销补偿 | **0** | gcc 的 target 已是 RTP 层，再乘 1.4 会让线速超链路（实测使 burst≥3 从 14% 恶化到 30%） |

### 3.2 状态机

```
healthy
  │  target < 需求 × 1.15 持续 500ms
  ▼
constrained
  │  发送队列打满
  ▼
degraded
  │  持续 10s 且连续 2 次确认
  ▼
evicted（主动断连，交给客户端重连）
```

恢复门槛比进入高（1.3×），避免阈值附近反复迁移。断连代价最高，所以额外要求两次确认。

## 四、指标与口径

三类分开，因为只有第一类能说「提升」：

| 类 | 定义 | 能否算提升 |
|---|---|---|
| **可对比** | 升级前后都存在 | ✅ 能算百分比 |
| **新增** | 升级后才有 | ❌ 只能判达标 |
| **守卫** | 不该变差 | ❌ 只能判没退化 |

### 4.1 可对比

| 指标 | 口径 | 目标 |
|---|---|---|
| 连续丢 ≥3 帧占比 | `len≥3 次数 / 总 burst 事件数`，**绝对次数不可比**（同配置下摆动 5 倍） | 下降 ≥30% |
| RTCP 丢包率 | `FractionLost`，p50/p99 | 与 burst 交叉验证 |
| RTCP 抖动 | RR 的 `Jitter` | 不恶化 |
| 断连次数 | ICE 进入 failed/disconnected 且未自愈 | 下降 ≥50% |
| 下行字节速率 | 服务端 `tx_bytes`，按 kind 分 | 与目标码率对照 |

### 4.2 新增

| 指标 | 口径 | 目标 |
|---|---|---|
| 平滑发送排队延迟 | 入队到出队，p99 | ≤ 60ms |
| 发送队列深度 | 每 tick 采样 | ≤ 6 包 |
| 发送丢弃 | 按 reason 分 | 稳态为 0 |
| 带宽目标值 | 估计器输出 | ≥ 60kbps（正常网络） |
| 状态迁移次数 | 每次迁移 | ≤ 2（阈值附近不抖） |
| 房间编码码率 | 档位变化 | 记录即可 |

### 4.3 守卫

| 指标 | 目标 |
|---|---|
| 正常网络播放缓冲延迟 | 回退 < 10ms |
| 建连耗时 | 回退 < 10% |
| 首次出声 | 回退 < 10% |
| 进程 CPU | 增幅 < 20% |
| goroutine 数 | 增幅 < 10% |

## 五、测试方法

### 5.1 四档场景

| 档 | 丢包 | RTT | 带宽 | 用途 |
|---|---|---|---|---|
| N0 | 无 | 无 | 不限 | 守卫指标基准 |
| N1 | 1% | 80ms | 不限 | 轻度劣化 |
| N2 | 5% | 200ms | 不限 | 中度劣化 |
| N3 | 15% | 400ms | 40kbps | 重度劣化 |

### 5.2 真实拥塞档

**上面四档测不出拥塞控制的价值** —— `netem loss` 是随机丢包，少发不会减少误码。

必须另设一档制造 bufferbloat：

```bash
tc qdisc add dev ifb0 root handle 1: htb default 10
tc class add dev ifb0 parent 1: classid 1:10 htb rate 30kbit burst 3k cburst 3k
tc qdisc add dev ifb0 parent 1:10 handle 20: netem delay 50ms limit 50
```

队列真实积累到 50 包（约 1.3 秒），延迟上涨才能被估计器检测到。

**为什么不能用另外两种**：

| 方案 | 问题 |
|---|---|
| `tbf ... latency 400ms` | 延迟封顶后直接丢包，估计器看不到「延迟持续增长」，误判不拥塞 |
| `netem ... rate 40kbit` | 均匀丢包，同样无延迟增长；缓冲给大时 30 秒都填不满 |

### 5.3 三个环境坑

1. **netem 必须只匹配 UDP**。`u32 match u32 0 0` 会把 TCP 信令一起丢，5% 就足以掐断 WebSocket
2. **netem 必须建连之后再挂**。否则登录与进房阶段先被拖垮
3. **每档开始前重启服务端**。累计指标不清零，多档数据会混在一起

## 六、风险与已知问题

| 风险 | 状态 |
|---|---|
| 装配顺序错导致估计器静默失效 | 已用固定顺序 + 单测覆盖 |
| 初始码率取默认 10kbps 会一上来就丢包 | 显式设 64kbps |
| 发送队列无界导致拥塞变延迟 | 已改为双上限 |
| **RTP 层与线路层口径混淆** | **已发生**：开销系数 400‰ 让线速超链路，burst≥3 从 14% 恶化到 30%，修正为 0 才拿到改善 |
| 每对端泄漏平滑发送协程 | 链路 Close 转发估计器 Close |
| 每对端一个采样协程 | 改为房间级单协程轮询 |
| 指标基数爆炸 | 禁止 ID 进 label |
| 误踢用户 | 双阈值 + 停留时间 + 2 次确认 |
| 降码率引起音质投诉 | 30% 占比门槛 + 升慢降快 |
| 中继队列 50→8 的回归 | 4 人房实测积压恒为 0，初步验证 |
| 关闭开关后行为不等价 | false 时不注册拦截器，而非内部 noop |
